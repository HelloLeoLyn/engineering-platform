## 1. Review 边界与原则

正式边界（ADR-001）：

- **Engineering Platform = 拿什么开发**：只拥有 Engineering Standards / Reusable Engineering Assets / Project Modeling / Resolution / Generation / Engineering Conformance 六域。
- **AI Dev OS = 怎么开发**：拥有 Planning / Orchestration / Agent Runtime / Tool-MCP Control / Approval / Retry-Timeout / Browser / Task Verification / Human Acceptance / Execution Audit。

Review 原则：

1. 每项只能得到一个 Primary Decision：KEEP / SPLIT / DEPRECATE / MOVE_TO_AI_DEV_OS。
2. **不迁移重复代码**：AI Dev OS 审计确认 Agent Execution / Tool Guard / Approval / Retry / Timeout / Execution Log 已有更成熟生产实现。MOVE_TO_AI_DEV_OS 的正确含义 = AI Dev OS 是 authoritative owner；EP V0.1 implementation 走 freeze → deprecate → compatibility period → future removal，**不得把 EP implementation 复制到 AI Dev OS**（避免第二套实现）。
3. WorkItem 不沿用审计初判，按字段语义重新拆解（§4.1）。
4. 成熟度分级仅作参考（审计报告）；本 review 只定 Ownership。

## 4. 关键拆解说明

### 4.1 WorkItem 字段级拆解（SPLIT 依据）

| WorkItem 语义 | 归属 |
|---|---|
| acceptance criteria 类型（BUILD/TEST/FILE_SCOPE/ARTIFACT） | EP（Engineering Conformance input） |
| scope 契约（允许/禁止文件范围） | EP（Conformance 校验输入；同时作为 AI Dev OS 工具授权参考） |
| 验收证据要求（Evidence 引用） | EP（Conformance 证据规范） |
| 状态机（OPEN/IN_PROGRESS/DONE 等任务流转） | AI Dev OS（Development task lifecycle） |
| 任务执行/Agent 关联 | AI Dev OS |

**桥接方式**：AI Dev OS Task 携带对 EP AcceptanceSpec（criteria+scope）的引用；EP Conformance 验证产出 ConformanceResult 回传 AI Dev OS，作为 Task Verification 的一个输入。

### 4.2 两类 Safety 分离（Tool Guard SPLIT 依据）

- **Generator 内部安全不变量（EP-owned，不得因 MOVE 删除）**：Path Safety、Ownership Safety、Overwrite Policy、Transaction Safety、Precondition（expectedBeforeHash）、Rollback——属于 GeneratorExecutor 正确性/安全的一部分，属于 IN SCOPE Generation 域。
- **Agent 工具授权（AI Dev OS-owned）**：Agent ToolPolicy、MCP Policy、Shell/Git/Docker/Browser authorization、Approval。
- 共用组件（PathSafety）按消费方归口：Generator 内部使用保留；Agent-facing guard 由 AI Dev OS ToolPolicy 取代。

### 4.3 两种 Verification 分离

- **Engineering Conformance Verification（EP）**：manifest 正确性、架构规则、依赖规则、capability/provider 兼容、生成结构、平台标准。
- **Development Task Verification / Acceptance（AI Dev OS）**：requirement satisfied、build/test/browser/security、任务验收、human approval。
- **集成方向**：AI Dev OS Validation Center →（provider）→ EP Conformance → ConformanceResult → 作为 Task Verification 的一个输入。不得合并为同一平台职责。

### 4.4 TestPlan/TestRun 收敛

- EP 不再维护"通用测试计划/执行记录"；收敛为 **Conformance Test Specification + ConformanceResult**。
- 实际测试执行/运行记录以 AI Dev OS testagent（TestPlan）与 validation（ValidationRun）为 authoritative。

## 5. Integration Contracts（架构定义，不创建 Schema/Java API）

最小集成边界（AI Dev OS → Engineering Platform，方向唯一）：

| Contract | 方向 | 内容 | 形态建议 |
|---|---|---|---|
| ProjectResolutionRequest/Result | AI Dev OS → EP | 解析 Project（Manifest → EPM） | 只读服务调用 |
| EffectiveProjectModel | EP → AI Dev OS | 工程事实（模块/能力/依赖/兼容性）供任务规划上下文 | 只读模型 |
| RegistryQuery | AI Dev OS → EP | 查询 Module/Capability/Provider 资产 | 只读查询 |
| GenerationRequest/Result | AI Dev OS → EP | 请求 GenerationPlan / 执行生成；写文件操作须经 AI Dev OS ToolPolicy 授权 | 服务调用（AI Dev OS 为控制方） |
| ConformanceRequest/Result | AI Dev OS Validation → EP | 提交 Conformance 校验；返回 ConformanceResult 作为 Task Verification 输入 | Validation provider 形态 |

原则：EP 只暴露工程能力/事实/操作；编排、审批、调度、Agent 选择、工具授权全部留在 AI Dev OS。

## 6. Migration Principles

1. **不复制实现**：AI Dev OS 已有成熟实现的能力（Agent Execution / Tool Guard(Agent 侧) / Approval / Retry / Timeout / Execution Log / ImplementationTasks 执行侧），**不得**把 EP implementation 复制到 AI Dev OS——避免第二套实现。
2. **MOVE 项执行路径**：EP freeze（不再扩展）→ deprecate（文档标注）→ compatibility period（V0.1 契约继续工作）→ future removal（precondition 满足后）。
3. **SPLIT 项执行路径**：EP 保留契约/语义部分（criteria/scope/conformance 规格/Generator 安全不变量），移除 runtime/task 语义；执行侧由 AI Dev OS 承接。
4. **删除前置**：任何移除前须（a）对应 AI Dev OS 能力已稳定（当前大多已满足）；（b）集成契约（§5）已建立；（c）用户明确批准 + 版本计划（V0.2+）。
5. **兼容性**：V0.1 全部契约在 compatibility period 内保持可用（ADR-001：不得破坏兼容性）。
