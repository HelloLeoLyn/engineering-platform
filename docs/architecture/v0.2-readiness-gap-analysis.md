# V0.2 Gap Analysis

- **日期**: 2026-08-14 ｜ **基线**: v0.1.0 + main 47abf8e
- **依据**: ADR-001 / system-boundary / v0.1-legacy-ownership-review + 当前真实代码、Schema、Registry、资产库、测试
- **范围**: 仅六域（Standards / Assets / Modeling / Resolution / Generation / Conformance）；AI Dev OS 域不分析

---

## 1. 六域成熟度

| 领域 | M0-M4 | 一句话证据 | 最大 Gap |
|---|---|---|---|
| 1. Engineering Standards | M2 | 4 类 Manifest Schema + docs/standards + ADR 齐备，build-time validator 6/6 | 标准未资产化：无 starter/模板规范落地，标准不参与生成 |
| 2. Reusable Engineering Assets | **M0** | templates/ modules/ providers/ capabilities/ backend/starters/ 全部 `.gitkeep` 空；registry 仅 modules 1 条 + errors 3 条 | **资产库零内容**（无模板/无 starter/无 provider/无 capability 数据） |
| 3. Project Modeling | M2 | Platform/Project/Module/Provider + Registry Schema 完整，fixtures 齐全，ManifestRuntimeValidator 最小实现 | 无真实项目 manifest 数据集；资产引用无法闭环（registry 空） |
| 4. Resolution | M2 | 13 步 pipeline 完整实现，测试覆盖充分（CompleteResolver 33 + Pipeline 14） | 只能解析 fixture：registry 空 → 真实输入必报 CAPABILITY/PROVIDER_MISSING；EPM 无实际项目消费 |
| 5. Generation | M1 | GenerationPlan + Executor（287 行：DryRun/Stager/Apply/Rollback/Transaction 真实实现），Planner 89 行骨架 | **无模板渲染/无内容源**：只能按 operation.content 写文件，无法生成真实项目结构 |
| 6. Engineering Conformance | M1 | Python schema validators + VerificationEngine（任务验收语义，已定 SPLIT） | Conformance 验证器未建：无架构规则/依赖规则/生成结构/平台标准验证（仅 schema 级 build-time） |

## 2. Top Gaps

**P0**
1. 资产库零内容（templates/starters/providers/capabilities 全空，registry 无数据）——六域全部断链的根因
2. Generation 无内容源/模板引擎——无法生成真实项目（只能写死内容）
3. 无依赖装配：Manifest 的 capability/provider 声明无法映射为 pom 依赖/配置
4. Resolver 无真实资产可解析——EPM 在真实项目上不可用
5. Conformance 验证器缺位——生成结果无"工程合规"证明

**P1**
1. 无 starter/模板规范（Java 25 + Spring Boot 基线未资产化）
2. 无代码生成（controller/service/mapper/配置类均手工）；无测试生成
3. 无真实项目 manifest 示例集（fixtures 是语法用例，非可解析资产集）
4. 资产元数据契约（asset manifest：模板/starters 如何声明、组合、版本）未定义
5. ManifestRuntimeValidator 仅最小结构校验，未接入完整 JSON Schema 语义

## 3. 真实价值测试

假设：新建 Java Web 项目（Java 25 + Spring Boot + persistence + validation + exception handling + audit + MyBatis-Plus + Q3）

| 步骤 | 结果 | 一句原因 |
|---|---|---|
| 声明项目 | **PARTIAL** | Schema 支持声明，但 capability/provider 资产不存在可引用 |
| Resolve | **PARTIAL** | Pipeline 可跑，但 registry 无 persistence/MyBatis-Plus 资产 → 必报 PROVIDER/CAPABILITY_MISSING |
| 选择真实资产 | **NO** | 资产库全空，无任何 provider/starter 可选 |
| 生成真实项目 | **NO** | 无模板/内容源，Planner 无法产出项目结构 |
| 装配依赖 | **NO** | 无 capability→依赖映射，pom 生成不存在 |
| 生成代码配置 | **NO** | 无代码/配置生成 |
| 生成测试 | **NO** | 无测试生成 |
| Conformance | **PARTIAL** | Schema 校验可跑；架构/依赖/结构合规验证不存在 |
| 最终可编译 | **NO** | 无法生成任何可编译项目 |

## 4. 核心结论

**V0.1 当前更接近 A：Framework/Contracts**

原因（≤5）：
1. 六大资产目录全空 + registry 仅 1 条示例——"可复用资产平台"无资产
2. Generation 无模板/内容源，无法产出真实项目（机制完整、内容缺失）
3. Resolver 只能解析 fixture，真实输入必然缺失资产错误
4. 无依赖装配/代码生成/测试生成
5. 177 项测试全部是契约与机制测试，无一真实项目端到端

## 5. V0.2 候选 Theme（≤3）

1. **Reusable Asset Platform（资产优先）**
   - 解决：资产库零内容、registry 无数据、资产元数据契约缺失
   - 价值：让 Modeling/Resolution/Generation 有真实输入；"拿什么开发"有实际内容
2. **Generation Pipeline v1（真实生成）**
   - 解决：无模板引擎、无依赖装配、无代码/测试生成
   - 价值：从 Manifest/资产产出可编译项目；闭环"复用+配置+生成"
3. **Engineering Conformance Validator v1**
   - 解决：合规验证缺位
   - 价值：生成结果可证明合规；为 AI Dev OS Validation provider 提供 ConformanceResult

## 6. 最终推荐

**Engineering Platform V0.2 = Reusable Engineering Asset Platform**：以资产库（templates/starters/registry 数据 + 资产元数据契约）为核心，打通 Modeling → Resolution → Generation → Conformance，使一个真实 Java 项目可声明、可解析、可生成、可验证。

（资产是唯一 P0 根因：无资产则 Resolve/Generate/Conformance 全部无输入；资产就绪后 Theme 2/3 才有内容可处理。）

## 7. Anti-Goals（≤8）

1. 不实现 Agent / OpenClaw / Codex Adapter
2. 不实现 Approval / Retry / Timeout 编排
3. 不实现 Browser Automation
4. 不实现 Tool / MCP orchestration
5. 不扩展 V0.1 Legacy（WorkItem 任务语义等 12 项之外不新增）
6. 不复制 AI Dev OS 实现（不迁移代码）
7. 不做第二套通用 TestRun/Verification（Conformance 聚焦，不重建任务验收）
8. 不实现 AI 规划/调度/AI workflow

## 8. Open Questions（≤5）

1. 资产粒度与 V0.2 覆盖范围：先做哪类 starter（Spring Boot Web 基础）与哪些 capability（persistence/validation/audit）？
2. 模板形态：自有模板目录（资产即目录）vs 引入渲染引擎——是否足够用"资产即代码"起步？
3. 依赖装配数据从哪来：capability → pom 依赖映射内置 vs provider manifest 声明？
4. Conformance 验证器与 AI Dev OS Validation provider 的对接契约何时定（V0.2 内还是并行）？
5. 资产库内容来源：从现有 backend/（sample-customer、platform-core/web/data）反向提炼为资产，还是全新编写？
